五、反思/分析/建议

  1. 官方点检先于重建，避免无效重算：本次先用 git ls-remote / git diff --stat 证实「36 包不变、仅版本标注」，从而只改标注、不重算包级图，节省大量成本。建议：每次版本升级先做包级结构与依赖线的作用域判定，再决定重算范围。
  2. 门控期望值须与产物同源：quality-gate.py 硬编码 119 与 headless 硬编码 119 是本次唯一 FAIL 的来源，说明期望值应尽量从 modified-dag.json.stats 动态取，减少手改遗漏。建议：后续把节点/组/装配/外部/机制计数改为从 stats 读取。
  3. 基线标注要显式且可机检：内部结构沿用旧基线时，在节点页副标题与 README 写明「内部结构基线 v1.18.29，v1.18.30 结构未变」，使 T3 的 grep 命中可被归类为「已声明基线」而非残留。建议：把该标注字符串固化为生成脚本参数，避免人工漏标。
  4. 中间数据版本串治理：stage-00-version-baseline.json 与采集脚本的版本串是本轮最易漂移处，属「数据与标注分叉」。建议：以单一真相源（一个 version 常量）派生所有脚本路径与输出文件名，配合一次引用普查。
  5. drawio 链路的超时韧性：drawio MCP 超时不影响最终交付，但暴露单点脆弱。建议：为导出步骤加超时重试 + 导出后 PNG bbox/尺寸双重校验。
