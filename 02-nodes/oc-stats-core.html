stats-core

oc-stats-core · package · G17-Stats · Layer 0

① 作用

Stats 后端核心（Effect + drizzle + PlanetScale）。src/athena.ts 封装 AWS Athena 查询服务（StartQuery/轮询/取结果），src/database.ts 提供 Effect 风格 DatabaseConfig/DrizzleClient，src/domain/ 下按 model/provider/geo/home/inference 分域定义聚合类型与查询，src/stat-sync.ts 实现 Athena → 数据库的增量/全量同步管线。src/index.ts 聚合导出全部命名空间。

② 提供能力

· Athena 查询服务：执行/轮询/分页取数（src/athena.ts:45）
· Effect 化数据库层：PlanetScale drizzle + schema + 迁移（src/database.ts:24,40）
· 统计领域模型：StatBaseAggregate 聚合结构与 grain day/week（src/domain/stat.ts:6）
· Model/Provider/Geo 统计仓库与 upsert（src/domain/model.ts 等）
· 首页聚合查询（getStatsHomeData，src/domain/home.ts:9）
· 统计同步管线：Athena 查询 → 聚合 → 写入（src/stat-sync.ts:23）
· App 配置（stage/publicUrl）与运行时（src/config.ts、src/runtime.ts）

⑤ 为什么存在（why）

设计意图（官方）

用 Effect 服务（Context.Service + Layer）组织全部依赖（Athena/Database/Config），运行时以 Layer 注入——与 console-core 的 fn 风格不同，stats 选择了纯函数式依赖注入，便于 Lambda/Server 两种宿主复用同一套查询/同步逻辑；Athena 只扫一次源表的 GROUPING SETS 设计明确为降成本优化。

改造关联

本机未改。装配层在多源数据归一化统计（如 0817 DAG 的包统计、github-dag 的 commit 统计）上复用了其思路：统一 schema 归一化 + 增量锚点窗口，但用 Python 而非 Effect。

⑥ 怎么用（how）

怎么用

Effect 生态服务包：Athena service（@aws-sdk/client-athena，StartQueryExecution→GetQueryExecution→GetQueryResults 轮询 300 次，WorkGroup/Catalog/Database 来自 Resource.InferenceEvent）；Database service（@planetscale/database + drizzle-orm/planetscale-serverless，DATABASE_URL 或 Resource.StatsDatabase.url）；domain/ 下 inference/model/provider/geo/stat（buildStatsQuery 用 GROUPING SETS 一次扫描聚合 sessions/requests/tokens/cost/duration/TPS 等指标）；stat-sync.ts 增量/全量同步（锚定 ISO 周、5 分钟摄取滞后、56 天展示窗口）。scripts: db:migrate / db:push / honeycomb:backfill / ensure-unique-users。

典型场景与协作

统计数据的采集-聚合-落库核心：Lambda（stats/function→core）与 stats-server 共用；honeycomb-backfill 把历史遥测灌入 Athena；migrate/ensure-unique-users 维护 PlanetScale 统计表。
