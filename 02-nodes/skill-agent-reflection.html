⑤ 为什么存在（why）

历史引入动机

2026-08-05 由 Reflection 系统设计部署时创建（Reflection 系统本身非反思产物，而是基础设施——Hermes 式自进化系统的核心 Skill）。0805-Reflection系统设计文档记载：用户发现当前仅有 Plan-and-Execute 模式，缺少系统化 Reflection 层（MEMORY.md 事后反馈、留档反思段、openspec-verify 都是零散被动的），参考 Hermes Agent 自进化架构（Background Review/Curator/Skills+Memory 双轨），35 项决策收敛后实现。动机三优先级：持续自我改进 > 减少重复错误 > 提升 Plan 质量。架构：Plan+Build 周期结束封装 4 层输入写 pending.json，下轮启动委派 reflection-worker（Flash 仅文件读写）分析产出 memory/skill 条目，/reflection 交互确认后写入 MEMORY.md 或 Reflection/skills/。

当前需求驱动

是全部 Reflection skills 的母系统：每个 Plan+Build 周期结束自动触发反思沉淀，维持"系统越用越聪明"的进化回路；当前 0817 批量确认的 DAG/cdisk/github 等 7 个 skills 均由本系统的 reflection-worker 提炼（pending.json 有完整 skill_entries 证据）。

⑥ 怎么用（how）

触发方式

MEMORY.md 自引用规则：用户下一条消息时主Agent 检查 meta.waiting_count>0 自动加载；用户随时 /reflection 交互式逐条确认 pending 条目；触发词 reflection、同步记忆、反思。

工作流/用法

· Plan+Build 周期结束 → 主Agent 封装 4 层输入写 pending.json（waiting）
· 下一轮用户消息 → 委派 reflection-worker（Flash，仅文件读写）分析产出 memory/skill 条目（status=done），主Agent 不阻塞继续正常流程
· 用户 /reflection → 逐条确认 → Memory 写 MEMORY.md（§-分段）/ Skill 写 Reflection/skills/{category}/{name}/SKILL.md → 条目 confirmed

协作关系

调度 reflection-worker 子Agent；产出物（Reflection skills/memory）供全部主Agent 加载；与 MEMORY.md、留档系统、agent-protocol.md 深度耦合
